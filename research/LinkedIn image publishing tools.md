# Pick Zernio, keep LinkedIn's API as backstop

*Research report, 9 November 2026. Question: which tools can programmatically publish image posts to Shweta Mehta's personal LinkedIn profile from scheduled Claude cloud sessions, one post per weekday, and what should be primary and backup?*

LinkedIn's own official API can publish image posts to a personal profile. The self-serve "Share on LinkedIn" product grants `w_member_social`, which the versioned Images API and Posts API accept with a `urn:li:person:` owner and author. That is the flow `engine/linkedin.py` already implements, so the official API meets the condition for being the backup. For the primary, the best fit is **Zernio (formerly Late)**, wired in as a second backend of `python -m engine publish`. It uses LinkedIn's official OAuth, supports personal profiles, has a REST API and a hosted MCP server, reportedly charges nothing for the first two connected accounts, and says it returns analytics for personal posts published through it. No self-serve LinkedIn app can get those analytics. If a live check shows Zernio's free tier excludes the API or image uploads, use **Upload-Post Basic at $24/month**, whose image endpoint and pricing are documented on its own pages. Composio's toolkit can post images, but only through a file-object (`s3key`) handoff that nobody has tested end to end here, and it has twice shipped a retired LinkedIn-Version header. It is a workaround, not a foundation. Most facts in this report come from search-result snippets because every vendor site, Microsoft Learn and docs.composio.dev were blocked from the research sessions. No INR prices were found for any tool. The verification list near the end says what to confirm on live pages before Shweta pays for anything.

## The official API already does image posts, with three costs

The image flow is well established. You call `POST /rest/images?action=initializeUpload` with owner `urn:li:person:{sub}`, PUT the bytes to the returned `uploadUrl`, then call `POST /rest/posts` with `content.media.id` set to the `urn:li:image:...`. The post URN comes back in the `x-restli-id` header ([Postproxy](https://www.postproxy.dev/blog/linkedin-api-automate-company-page-publishing/); [Blotato](https://www.blotato.com/blog/linkedin-posting-api)). The Images API accepts **`w_member_social`** among its scopes ([truto.one](https://truto.one/integrations/detail/linkedinpersonal/); [Adaptly](https://adaptlypost.com/blog/linkedin-initializeupload-image-urn)), and `w_member_social` is an open, self-serve permission with no review gate ([closelyhq](https://blog.closelyhq.com/linkedin-api-for-developers-what-you-can-and-cant-do); [flaghand](https://flaghand.com/docs/guides/linkedin-api-personal-profile)). Versioned `/rest/` calls need `LinkedIn-Version: YYYYMM` and `X-Restli-Protocol-Version: 2.0.0`. A missing header returns 400, a sunset version returns **426 NONEXISTENT_VERSION**, and each version lives at least a year ([Adaptly](https://adaptlypost.com/blog/linkedin-version-header-format-required); [Microsoft Learn versioning](https://learn.microsoft.com/en-us/linkedin/marketing/versioning)). The repo pins `"api_version": "202606"` in `config/settings.json`. That is safe today, but someone must bump it before it sunsets, presumably around mid-2027 (an inference from the one-year minimum). The legacy `/v2/assets` + `/v2/ugcPosts` route is still documented on the Share on LinkedIn page, but it is labelled legacy and has no published sunset date ([Microsoft Learn, mirror](https://learn.microsoft.com/ru-ru/linkedin/consumer/integrations/self-serve/share-on-linkedin); [timetopost](https://timetopost.co/blog/how-to-post-to-linkedin-api/)).

Limits will not bind at this volume. Images must be under **36,152,320 pixels** in JPG, PNG or GIF ([Microsoft Learn Images API, search summary](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/shares/images-api?view=li-lms-2026-10)). No official per-file MB cap was found, and third-party guides quote 5 to 20 MB ([PublishQ](https://publishq.com/linkedin-limits)), so keeping images under about 5 MB is the safe rule. LinkedIn does not publish standard rate limits. Limits reset at midnight UTC and an overage returns 429 ([Microsoft Learn rate limits](https://learn.microsoft.com/en-us/linkedin/shared/api-guide/concepts/rate-limits)). Third parties cite **150 requests per member per day** for Share on LinkedIn ([Adaptly](https://adaptlypost.com/blog/linkedin-post-limit-per-day)), against roughly 3 to 4 calls per image post.

The three costs are these. First, **tokens last 60 days** ([Microsoft Learn OAuth](https://learn.microsoft.com/en-us/linkedin/shared/authentication/authorization-code-flow)). Programmatic refresh tokens, which last 365 days and do not reset on use, go only to approved partners ([Microsoft Learn refresh tokens](https://learn.microsoft.com/en-us/linkedin/shared/authentication/programmatic-refresh-tokens); [opentweet](https://opentweet.io/answers/linkedin-api-token-expires-60-days)). Shweta would re-authorize in a browser about every 55 days. Second, creating any developer app requires a **LinkedIn Company Page** whose admin verifies the app ([Zernio](https://zernio.com/blog/linkedin-posting-api); [OWOX](https://docs.owox.com/packages/connectors/src/sources/linked-in-pages/credentials/)). The app still posts to her personal profile. A minimal TrainWithShweta page would do, and setup is likely same-day because nothing needs review. Third, there are **no personal-post analytics**. `memberCreatorPostAnalytics` needs `r_member_postAnalytics` from the Community Management API, which LinkedIn says is "only available to registered legal organizations for commercial use cases" ([Microsoft Learn app review](https://learn.microsoft.com/en-us/linkedin/marketing/community-management-app-review); [Member Post Statistics, search summary](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/members/post-statistics?view=li-lms-2026-09)). Requesting that scope before approval breaks the consent screen ([GitHub issue #695](https://github.com/christopherqueenconsulting/linkedin_engagement_manager/issues/695)). Whether a sole-trader business would qualify is untested.

## Composio can post images, but only through an untested handoff

Composio's create-post tool does accept images. The live tool schema, read through the connected Composio MCP on 9 Nov 2026 (it has no public URL), shows `LINKEDIN_CREATE_LINKED_IN_POST` taking `images` as an array of 1 to 20 objects of the form `{name, mimetype, s3key}`. There is **no URL, base64 or image-URN field**. The `s3key` must point at a file already in Composio's own storage. That explains why Shweta sees text work and images fail: an agent passing a public image URL or local path has nowhere to put it. Composio also exposes `LINKEDIN_INITIALIZE_IMAGE_UPLOAD` (Images API) and `LINKEDIN_REGISTER_IMAGE_UPLOAD` (legacy assets), but its own description tells you to "use the image URN in CREATE_LINKED_IN_POST" while the create-post schema has no field for one. The two tools don't fit together.

A workaround exists on paper. In Composio's remote workbench, fetch the image into the sandbox, call `upload_local_file()` to get an `s3key`, then call create-post with that key against the default connection `linkedin_libra-rifter` (author `urn:li:person:I5qjBjt3sE`). Composio's `proxy_execute` could instead call `/rest/images` and `/rest/posts` directly with Composio's stored token (live tool description, 9 Nov 2026). Neither was tested end to end, deliberately, because a test would publish a real post. The bigger worry is reliability. Two GitHub issues document create-post failing with **426 NONEXISTENT_VERSION** because Composio pinned the retired header `20241101`, with or without images ([#4320](https://github.com/ComposioHQ/composio/issues/4320); [#3113](https://github.com/ComposioHQ/composio/issues/3113)). Composio also has no LinkedIn post-analytics tool. A search for one returned only the Ordinal toolkit. As an engine backend, Composio adds a hop and a versioning risk the engine doesn't have, and it still sits on a 60-day member token unless Composio's app has partner refresh access, which is unknown.

## API-first services split on connection method and analytics

Five of the six services connect through LinkedIn's official OAuth. **Unipile** is the exception. It links the member's own session through the `li_at` cookie, username and password, or a browser extension ([Unipile docs](https://developer.unipile.com/v2.0/docs/linkedin-link-accounts)), and its own material warns that logging in this way "may trigger a warning from LinkedIn" ([Unipile guide](https://developer.unipile.com/docs/linkedin)). That is session automation with ToS and restriction risk to Shweta's main business profile, so it is ruled out regardless of features.

Among the OAuth services, the deciding factors are price and personal analytics. **Ayrshare** has the best-documented personal analytics: personal profiles return an expanded set after a re-link, with data lagging 24 to 48 hours ([Ayrshare updates](https://www.ayrshare.com/docs/whatsnew/latest); [Ayrshare analytics](https://www.ayrshare.com/docs/apis/analytics/social)). But it costs about **$149/month** for one profile ([Ayrshare pricing, search summary](https://www.ayrshare.com/pricing/)), heavy for a solo coach. **Zernio** charges per account: **first 2 accounts free**, then $6 each for accounts 3 to 10, "as of October 2026" ([thatmarketingbuddy](https://thatmarketingbuddy.com/pricing/zernio)). It covers "personal & company pages" ([getlate.dev/linkedin](https://getlate.dev/linkedin)), runs a hosted LinkedIn MCP, and says LinkedIn returns stats for personal-profile posts published through Zernio at no extra cost ([Zernio LinkedIn MCP](https://zernio.com/linkedin-mcp)). The weak points are conflicting pricing sources (older flat plans at $13 and $33, and a "from $29" headline) and an image field nobody has seen in the docs. **Upload-Post** is the most transparent. Its LinkedIn endpoint "publishes your video or image to the connected LinkedIn profile" ([Upload-Post LinkedIn](https://www.upload-post.com/platforms/linkedin/)), it has an MCP server, and its own pricing docs list Free at 10 uploads/month and **Basic at $24/month** with unlimited uploads ([Upload-Post pricing](https://docs.upload-post.com/resources/pricing-and-limits)). Free won't cover about 22 weekday posts, and its analytics API covers company pages only ([Upload-Post analytics](https://docs.upload-post.com/api/get-analytics/)). **Blotato** costs $29/month, its trial excludes the API, and its analytics exclude LinkedIn ([Blotato AI info](https://www.blotato.com/ai-info)). **Postiz** documents `upload` and `upload-from-url` endpoints ([PR #2281](https://github.com/gitroomhq/postiz-app/pull/2281)) and costs about $29/month on cloud or $0 self-hosted. Self-hosting needs your own LinkedIn app, so it has the same 60-day token as the engine, and personal analytics remain an open feature request ([issue #1680](https://github.com/gitroomhq/postiz-app/issues/1680)).

No vendor states a concrete re-auth interval for personal LinkedIn connections. If a vendor holds partner refresh-token access, re-consent could stretch to about a year. If not, it's 60 days, the same as the engine's own token. Ask each vendor before buying.

## Schedulers and automation platforms add a layer without adding much

The mainstream schedulers all publish through official OAuth, and none was reported to use browser automation ([Later help](https://help.later.com/hc/articles/360063905933); [Ayrshare LinkedIn API](https://www.ayrshare.com/linkedin-api.md)). Their APIs vary. **Buffer** opened a GraphQL API and official MCP on every plan, Free included (1 key, 3,000 requests per 30 days) on 27 May 2026 ([Buffer blog](https://buffer.com/resources/buffer-api-is-here/); [Buffer help](https://support.buffer.com/article/859-does-buffer-have-an-api)). But images reportedly must already be hosted at a URL ([Buffer roadmap](https://developers.buffer.com/roadmap)), and Composio's Buffer tool is text-only. **Typefully** has the cleanest documented media flow, a presigned upload that returns a media_id ([obsidian-typefully docs](https://dsebastien.github.io/obsidian-typefully/api-features.html)), and a competitor says its API is on every plan including Free ([OpenTweet](https://opentweet.io/blog/typefully-pricing-2026)). LinkedIn analytics are reported as unavailable ([Kleo](https://kleo.so/blog/typefully-review)). **Ordinal** is the strongest LinkedIn-first option, with REST API, MCP, up to 20 assets per post and profile analytics ([Ordinal docs](https://docs.tryordinal.com/api/introduction.md)). But the API needs Pro at **$235 to $265/month** ([Ordinal pricing](https://tryordinal.com/pricing)). **Publer** gates its API to Business, where prices conflict at roughly $10 to $21 per account per month ([Publer help](https://publer.com/help/en/article/1c57hsq/)). **Metricool** gates its API to Advanced at about €43/month and keeps LinkedIn off Free ([Metricool help](https://help.metricool.com/plans-add-ons-and-api-access-explained-xux1u)). **Hootsuite**'s API is Enterprise-only ([upload-post review](https://www.upload-post.com/hootsuite-pricing/)). No usable public posting API was confirmed for **Later**, **SocialBee** or **Taplio**.

The automation platforms are thin wrappers over the same `w_member_social` API the engine calls. **Zapier**'s "Create Share Update" takes an image URL and is exposed on Zapier MCP ([Zapier help](https://help.zapier.com/hc/en-us/articles/8495987891853-How-to-get-started-with-LinkedIn-on-Zapier); [Zapier MCP](https://zapier.com/mcp/linkedin)). Zapier says outright that LinkedIn tokens expire after 60 days, and webhooks need Professional at about $19.99/month annual ([eesel.ai](https://eesel.ai/blog/zapier-subscription)). **Make**'s "Create a User Image Post" takes a file ([Make LinkedIn app](https://www.make.com/en/help/app/linkedin)) and fits within the Free plan's 1,000 credits ([eesel.ai Make](https://eesel.ai/blog/make-pricing)). **n8n**'s native node broke from about April to July 2026 on the same 426 version error ([n8n community](https://community.n8n.io/t/linkedin-node-fails-with-nonexistent-version-20250401-in-n8n-cloud-2-15-x/288332)). **Pipedream** has an open MCP image-post 403 bug ([#17752](https://www.goodfirstissue.org/PipedreamHQ/pipedream/issues/17752)) and reportedly moved production use to $99/month in October 2026 ([UsagePricing](https://www.usagepricing.com/blueprint/activity/pipedream-2026-10-04-startup-plan-replaces-tiers)). None of the four offers personal-post analytics. LinkedIn's Member Post Analytics API reaches about eleven approved vendors, Later among them ([Digiday](https://digiday.com/media/linkedin-makes-it-easier-for-creators-to-track-performance-across-platforms)), and a Zap or scenario doesn't inherit that approval.

## What to verify on live pages before committing

Every vendor site, Microsoft Learn and docs.composio.dev failed to load from the research sessions, so the following came only from snippets. Check them before paying or switching. For Zernio: that the "first 2 accounts free" model is current, that the free tier includes API access, the exact image field (URL or upload), and the personal-analytics claim. For Upload-Post: Basic at $24, and the image request format. For Ayrshare: the $149 price. For Buffer: whether the API attaches images, and how. For Typefully: whether the API is on Free. For every vendor: how often a personal LinkedIn connection must be re-consented, and whether any of them is an approved Member Post Analytics vendor. On LinkedIn's side, read Microsoft Learn directly for the current newest `LinkedIn-Version`, the sunset date of 202606, and whether the 150 requests/member/day figure still stands. Two facts here were checked against primary sources: Composio's create-post schema (live MCP, 9 Nov 2026) and the engine's existing Images + Posts implementation (`engine/linkedin.py`).

## Conclusion

The recommendation is **Zernio as primary and LinkedIn's official API as backup**, both behind `python -m engine publish`. The engine should get a `publisher` setting that selects a backend. The Zernio backend would upload the image from `content/images/`, create the post, and record the returned post ID in the slot record before reporting success, so locking and duplicate prevention stay in one place. An ambiguous failure must not fall through automatically to the other backend, or one slot could get two posts. The official backend already exists and needs only a token and a pinned version that is still live. Zernio earns the primary slot through what the official path can't supply: possible personal-post analytics that could flow back into the content engine, and a managed OAuth connection that may outlast 60 days. If verification knocks Zernio out, Upload-Post Basic takes its place, giving up analytics. If analytics matter more than cost, Ayrshare is the documented choice at about $149/month.

Primary and backup are close on raw capability. Publishing images through the official API is already solved in this repo, so a third-party primary is mainly worth paying for if its analytics claim holds up. If it doesn't, the cheapest reliable setup is to run the official API as primary and keep Zernio or Upload-Post on a free or low tier as the backup. Whichever comes first, the pipeline should treat 401 and 403 responses as "email Shweta to reconnect" rather than retrying, because every option short of a partner refresh token needs a human back at a consent screen every 60 days.
